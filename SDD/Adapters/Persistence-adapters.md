# Persistence Adapters Specification (Output Adapters)

## 1. Overview

Persistence Adapters reside in `nexusmarket/adapters/persistence/`. They implement the **Output Ports** defined in `nexusmarket/domain/ports/out/` (see [Output-ports.md](../domain/Output-ports.md)).

To guarantee complete technology independence and prevent persistence entities/ORM leaks into the domain:
1. Persistence adapters do NOT use domain models directly as database entities/documents.
2. Every output adapter defines its own **Persistence Entities / Documents (Repository DTOs)**, **Mappers** (Domain Model ↔ Entity/Document) and **Spring Data Repositories**.
3. The domain is not modified to accommodate persistence. Domain objects are rebuilt through their rehydration constructors (see [Domain Model.md](../domain/Domain%20Model.md)).

| Store | Technology | Content |
| ----- | ---------- | ------- |
| MySQL (`nexusmarket`) | Spring Data JPA / Hibernate | Every business aggregate (12 repository ports). |
| MongoDB (`nexusmarket`) | Spring Data MongoDB | Audit trail (`AuditLogRepositoryPort`). |

---

## 2. Architecture & Data Flow

```text
Domain Service (domain/services)
      |
      v  Calls Output Port Interface
Output Port Interface (domain/ports/out)
      ^
      |  Implemented by Output Persistence Adapter
Persistence Adapter (adapters/persistence)
      |  1. Maps Domain Model -> Repository Entity/Document
      |  2. Calls a Spring Data Repository
      |  3. On read, rebuilds the Domain Model (JpaAggregateLoader resolves references)
      v
Spring Data Repository (JPA / MongoDB)
      |
      v
Database (MySQL / MongoDB)
```

---

## 3. Technology Stack Guidelines

- **Relational (MySQL):** Spring Data JPA. Entities use `@Entity`, `@Table`, `@Id`, `@Column`; repositories extend `JpaRepository<Entity, ID>`.
- **NoSQL (MongoDB):** Spring Data MongoDB. Documents use `@Document(collection = "...")`, `@Id`; repositories extend `MongoRepository<Document, ID>`.

### 3.1 Mapping conventions

- **Flat entities:** relations between aggregates are stored as identifier columns (`buyer_id`, `seller_id`, `order_id`…). There is no `@ManyToOne` / `@OneToMany` between aggregates.
- **Catalogs** (enums implementing `DomainCatalog`) are stored as their `code` (`String`) and read back with `fromCode`.
- **Value objects:** `Address` and `Variant` are `@Embeddable` (`AddressEmbeddable`, `VariantEmbeddable`). Lists of value objects (product variants, buyer additional addresses) are `@ElementCollection` (eager, ordered with `@OrderColumn`).
- **Child rows** (`CartItem`, `OrderItem`, `InventoryMovement`) live in their own tables with the id of their parent and a surrogate `IDENTITY` key.
- **Identifiers:** aggregate ids are UUID strings generated by the domain services, never by the database.
- **Date ranges** use `GreaterThanEqual` + `LessThan` (exclusive upper bound), never Spring Data `Between`.
- One mapper per entity (static `toEntity` / `toDomain`), one Spring Data repository per table.

## 5. Adapter Design Decisions

### 5.1 `save` returns the same instance

Every `save(x)` writes the entity and returns the **same domain instance it received**, not a copy reloaded from the database. Services rely on object identity right after saving (for example `RegisterBuyerUserService` creates a `Cart` for a `Buyer` and calls `Buyer.assignCart(cart)`, which checks `cart.getBuyer() == this`). Since ids are assigned by the domain, nothing generated by the database needs to be read back. For the versioned entities (section 5.6) `save` and `update` write onto the managed entity of the current transaction instead of building a new one.

### 5.2 `JpaAggregateLoader`

`adapters/persistence/jpa/JpaAggregateLoader` is a Spring `@Component` that rebuilds domain objects whose references span several tables. Several adapters need the same chains (order → buyer → items → product → seller → warehouse), so they are resolved in one place using the Spring Data repositories, the mappers and the domain rehydration constructors.

| Method | Rebuilds |
| ------ | -------- |
| `requireUser(id, type)` | A `User` of the expected subclass (`Buyer`, `Seller`, `LogisticsOperator`, or `User`). |
| `toWarehouse` / `requireWarehouse` | `Warehouse` with its `Seller` (none for Marketplace). |
| `toProduct` / `requireProduct` / `requirePhysicalProduct` | `PhysicalProduct` or `DigitalProduct` with its `Seller` and variants. |
| `toInventory` | `Inventory` with its movement history. |
| `loadCartItems` | Cart items via `CartItem.rehydrate`. |
| `toOrder` / `requireOrder` | `Order` with buyer, items and shipments (no invoice, see 5.3). |
| `toShipment` | `Shipment` with origin warehouse and logistics operator. |
| `toReturnRequest` / `requireReturnRequest` | `ReturnRequest` with its `Order`. |

A referenced row that does not exist means the database is inconsistent and raises `IllegalStateException`. Query methods that receive an aggregate (`findByBuyer(buyer)`, `findBySeller(seller)`, `findByOrder(order)`, `findByProductAndWarehouse(...)`, `findByReturnRequest(...)`, `findByPerformedBy(user)`) reuse the instance supplied by the caller instead of reloading it.

### 5.3 Bidirectional references without cycles

| Relation | How it is rebuilt |
| -------- | ----------------- |
| `Order` ↔ `Shipment` | A base `Order` (items, no shipments) is built first; its shipments are built pointing to it; the final `Order` receives those shipments through the rehydration constructor. `Order` checks shipment ownership by id, so this passes its validation. |
| `Order` ↔ `Invoice` | A loaded `Order` never carries its invoice (`invoice = null`). `Order` checks the invoice by object identity and `attachInvoice` rejects a `DELIVERED` order, so it cannot be attached on load. The invoice is read with `InvoiceRepositoryPort.findByOrder` and points to its order. `GenerateInvoiceService` already checks `existsByOrder`. |

### 5.4 Inverse lists that are not loaded

These collections are the inverse side of a reference stored on the other aggregate. They are left empty on load (no domain service reads them) and are queried through their own port:

| Collection | Read through |
| ---------- | ------------ |
| `Buyer.cart` | `CartRepositoryPort.findByBuyer` |
| `Buyer.orders` | `OrderRepositoryPort.findByBuyer` |
| `Seller.warehouses` | `WarehouseRepositoryPort.findBySeller` |
| `Seller.products` | `ProductRepositoryPort.findBySeller` |
| `Warehouse.inventories` | `InventoryRepositoryPort.findByWarehouse` |
| `PhysicalProduct.inventories` | `InventoryRepositoryPort.findByProduct` |
| `Order.invoice` | `InvoiceRepositoryPort.findByOrder` (see 5.3) |

### 5.5 Writing child rows

| Child | Strategy |
| ----- | -------- |
| `CartItem` | Items change freely, so writing a cart deletes its `cart_items` rows and inserts the current ones (`@Transactional`). Items are rebuilt with `CartItem.rehydrate`, so an item whose product is no longer published is kept, not lost on the next save. |
| `OrderItem` | Immutable once the order exists: inserted on the first `save` only; `update` writes the order row. |
| `InventoryMovement` | Append-only: writing an inventory inserts the movements beyond the ones already stored (`@Transactional`). |

### 5.6 Optimistic locking (`@Version`)

Transactions are opened by the use case adapters (see [Use-cases-adapters.md](Use-cases-adapters.md), section 3); the persistence adapters join them. Three entities carry an optimistic lock version, because two concurrent use cases on the same row would otherwise both commit (lost update or overselling):

| Entity | Conflict it prevents | Version increment |
| --- | --- | --- |
| `InventoryJpaEntity` | Two buyers or operators reserving the last unit at the same time. | Automatic: every change modifies the row. |
| `OrderJpaEntity` | Paying, creating shipments or confirming the delivery of the same order twice at the same time. | Forced (`OPTIMISTIC_FORCE_INCREMENT`): some operations change the order only through other tables (shipments). |
| `CartJpaEntity` | Two concurrent changes of the same cart, or a change racing with `ConfirmOrderService`. | Forced (`OPTIMISTIC_FORCE_INCREMENT`): the cart row never changes; the items live in `cart_items`. |

The column is `version BIGINT NOT NULL DEFAULT 0`; the default lets `ddl-auto: update` add it to rows that already existed. The domain has no version field, so the adapters work as follows (example: `InventoryJpaAdapter` inside `reserveInventory` or `confirmOrder`):

1. The use case adapter opens the transaction and its persistence context.
2. `findByProductAndWarehouse` loads `InventoryJpaEntity`; it stays **managed** holding version `v`, and the mapper builds the domain `Inventory`.
3. The domain changes it (`registerMovement`).
4. `update(inventory)` gets the entity with `findById`, which returns the **same managed instance** from the persistence context (still version `v`), copies the domain fields onto it (`InventoryJpaMapper.copyToEntity`) and inserts the new movements. It never builds a new entity for an existing row.
5. On commit Hibernate runs `UPDATE inventories SET ..., version = v + 1 WHERE product_id = ? AND warehouse_id = ? AND version = v`. If another transaction committed first, no row matches: Hibernate raises an optimistic lock exception, Spring translates it to `ObjectOptimisticLockingFailureException`, the whole use case is rolled back (including the movements and the pending audit records) and the API answers **409** (see [Global-exception-handler.md](Global-exception-handler.md)).
6. A new row (`save` of an inventory, order or cart that does not exist) is persisted with version `0`.

`OrderJpaAdapter` and `CartJpaAdapter` do the same with `OrderJpaMapper.copyToEntity` / `CartJpaMapper.copyToEntity` and then call `EntityManager.lock(entity, LockModeType.OPTIMISTIC_FORCE_INCREMENT)`, so the version is checked and incremented even when the row itself did not change.

The protection relies on the transaction of the use case: outside a transaction there is no shared persistence context and the comparison would be against the current version instead of the one read at the start. Every call through the role ports is transactional. Other entities (`Product`, `Warehouse`, `Shipment`, `User`) are not versioned: their concurrent changes are idempotent or low-impact, and they can adopt the same pattern later.

## 7. MongoDB Adapter (`adapters/persistence/mongodb/`)

### 7.1 `AuditLogRepositoryPort` → `AuditLogMongoAdapter`

| Item | Value |
| ---- | ----- |
| Document | `AuditLogDocument` |
| Collection | `audit_logs` |
| Fields | `_id` (`id`), `action`, `performedById`, `performedByEmail`, `role`, `entityType`, `entityId`, `occurredAt`, `details` (`Map<String, String>`) |
| Mapper | `AuditLogMongoMapper` |
| Repository | `AuditLogMongoRepository`: `findAllByOrderByOccurredAtAsc`, `findByPerformedByIdOrderByOccurredAtAsc`, `findByEntityTypeAndEntityIdOrderByOccurredAtAsc` |

The trail is append-only (no update or delete).

**Write after commit.** The JPA transaction does not cover MongoDB. When a transaction is active, `save` registers a `TransactionSynchronization` (`TransactionSynchronizationManager`) and writes the document in `afterCommit()`:

* the use case **commits** → the records are written in registration order, right after the commit (read-only transactions also commit, so query and report audits are written);
* the use case **rolls back** → `afterCommit()` never runs and no audit record remains;
* MongoDB **fails after the commit** → the error is logged at `ERROR` with the data needed to rebuild the record (id, action, entity, user, date, details); the already committed operation is not failed;
* **no transaction** active (for example the `DatabaseSeeder`) → the record is written immediately and a MongoDB error propagates.

### 8.1 `PaymentGatewayPort` → `SimulatedPaymentGatewayAdapter`

There is no external payment provider in this phase. The adapter applies one configurable rule:

* `PaymentResult.APPROVED` when `Order.totalAmount()` is less than or equal to `app.payment.simulated.approval-limit`.
* `PaymentResult.REJECTED` when it is greater.

| Property | Default |
| -------- | ------- |
| `app.payment.simulated.approval-limit` (`PAYMENT_APPROVAL_LIMIT`) | `10000000.00` |

To test the rejection path, confirm an order whose total exceeds the limit, or start the application with a low limit (for example `PAYMENT_APPROVAL_LIMIT=1`). Each decision is logged with the order id, total, limit and result. `AuditLog` requires a fully built `User` as `performedBy`, which cannot be rebuilt from the document alone (`User` validates identification, email and password). The document keeps `performedById` plus the denormalized email and role for readability; on read the adapter loads the `User` from the MySQL `users` table through `JpaAggregateLoader.requireUser` (once per user per query). `findByPerformedBy(user)` reuses the supplied user.
